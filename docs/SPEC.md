# Searly Android app: v1 spec

Status: **planned**. Nothing in this document is built yet except the empty Expo scaffold at the
repo root. Protocol facts come from [PROTOCOL.md](PROTOCOL.md) and the Python reference client in
[experiments/python](../experiments/python); tags **[HW]** / **[APK]** keep their meaning from there.

## Goal

A small offline Android app that pairs with a ThermoMaven G1 over Bluetooth, shows live probe
temperatures, and starts or adjusts a cook. No account, no network permission, no analytics.

Done for v1 means: on a real Android phone and a real G1, a user can pair, see live readings,
start a Manual or Smart cook, change its target, change the volume, and reconnect after closing
the app without pressing a button on the G1.

## Scope

| v1 (Android, foreground) | Later |
|---|---|
| Pair (first time, OK button on G1) | Background monitoring with a foreground service |
| Reconnect with stored identity, no button | "Target reached" / "remove now" notifications |
| Live screen: probe and base status every 2 s | Smart states (`remove`, `resting`, `ready`) and ETA |
| Start Manual or Smart cook, change target | Resting target (action 4) |
| Volume setting | Other `setting:modify` fields ([APK] only today) |
| °C / °F display preference (local) | iOS build, multi-probe models, `BT:user:unbind` |

Out of scope: Wi-Fi setup, the cloud, recipes and doneness guides, stopping a cook over BT (the G1
ignores it while the probe is out [HW]; the UI says "dock the probe to end the cook" instead).

## Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | Expo SDK 58 (RN 0.88, new architecture), development build | Already scaffolded; config plugins keep `android/` generated |
| BLE | `react-native-ble-manager` 12.x + its config plugin | Actively maintained, has an Expo plugin, byte arrays in and out (no base64) |
| zstd decode | `fzstd` (pure JS) | The G1 sends real zstd; Hermes has no zstd |
| zstd encode | ~10 lines in `src/protocol`, uncompressed "raw block" frames | Commands are under 1 KB, so compression is pointless; avoids a native module |
| Identity storage | `expo-secure-store` | Holds `userId`, `deviceId`, peripheral id. Anyone with these can drive the G1 |
| Random ids | `expo-crypto` | `cmdId`, `cookUuid`, 18-digit `userId` / `deviceId` |
| Navigation | None. One root component switches on connection state; cook and settings are RN `Modal`s | Two screens do not need a router |
| Lint / format / test | `oxlint`, `oxfmt`, `vitest` (protocol layer only), `tsc --noEmit` | Repo defaults |

Expo Go cannot load the BLE module. Run with `npx expo run:android` (local dev build) or an EAS
development build.

### Raw-block zstd: verify first

The encoder writes a valid zstd frame with one uncompressed block:
`28 B5 2F FD | A0 | content size u32 LE | (len << 3 | 1) u24 LE | json`. libzstd decodes this
(checked against `zstandard` 0.25.0). The G1's ESP32 decoder has not seen it yet. **Before any app
code**, switch `pack()` in `g1.py` to raw blocks behind a flag and run `send WT10:setting:modify
'{"volume":"mute"}'` on hardware. If the G1 rejects it, fall back to a native zstd module.

## Architecture

```
index.ts, App.tsx                 root: permission gate, then PairScreen or LiveScreen
src/protocol/                     pure TypeScript, no React Native imports
  crc.ts                          CRC-16/XMODEM
  zstd.ts                         raw-block encode, fzstd decode
  envelope.ts                     pack / unpack the AA AA envelope (both CRCs checked)
  blufi.ts                        frames(seq, payload, chunk) and a Reassembler
  messages.ts                     message types, command builders, tenths-of-°F helpers
  protocol.test.ts                vitest, fixtures generated by g1.py
src/ble/g1.ts                     G1Session: scan, connect, MTU, notify, send, receipt, trust
src/useG1.ts                      React hook: connection state machine and latest status report
src/screens/                      PairScreen, LiveScreen, CookModal, SettingsModal
```

`src/protocol` ports `pack`, `unpack`, `frames` and the notify reassembly from `g1.py` one to one.
`G1Session` is the only code that touches `react-native-ble-manager`.

## BLE contract (Android)

| Step | Call | Notes |
|---|---|---|
| Start | `BleManager.start()`, `checkState()` | Prompt `enableBluetooth()` when off |
| Scan | `scan({ serviceUUIDs: ["ffff"], seconds: 20 })` | Keep results whose name starts `TM-WT10`. After pairing, look for the stored peripheral id first |
| Connect | `connect(id)` then `retrieveServices(id)` | |
| MTU | `requestMTU(id, 512)` | **Required.** Android starts at 23, frames are up to 259 bytes. Write chunk = `min(253, mtu - 3 - 6)` |
| Notify | `startNotification(id, "ffff", "ff02")`, `onDidUpdateValueForCharacteristic` | Feed bytes to the Reassembler |
| Write | `write(id, "ffff", "ff01", frame, frame.length)` once per frame, awaited in order | **Pass `maxByteSize`**: it defaults to 20 and the library would split frames itself |
| Disconnect | `onDisconnectPeripheral` | Reset `seq` and the Reassembler; keep `cmdSeqNo` |

All writes go through one promise queue so frames from two commands never interleave.

Unknown [HW]: whether the G1 fragments its own notifications to the negotiated MTU. Log notify
lengths during the first hardware run; if the G1 assumes MTU 500 and Android negotiates less,
notifications will truncate and `unpack` will fail its CRC.

### Permissions

Config plugin with `neverForLocation: true`: `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` on Android
12+, `ACCESS_FINE_LOCATION` capped at SDK 30 for older phones. Request at runtime with
`PermissionsAndroid` before the first scan. The app itself needs no `INTERNET` permission, but the
React Native template adds it and development builds need it for Metro. Removing it from release
builds is a later task.

## Session state machine

```
no-identity ──pair──▶ pairing ──success──▶ live
identity ──▶ scanning ▶ connecting ▶ trusting ──success──▶ live
                                       └── cmdError 11 ──▶ needs-repair (keep identity, offer re-pair)
live ──disconnect──▶ reconnecting (1, 2, 5, 10 s, then every 10 s) ──▶ scanning
any step ──BT off / permission denied / scan timeout──▶ error (reason + retry)
```

Reconnect only while the app is in the foreground in v1.

### Pairing [HW]

1. Screen: "Put the probe in the dock". Button: Pair.
2. Generate `userId` and `deviceId` (18 random digits each, first digit non-zero).
3. `BT:apply:trust` with `mode: "pair"`, envelope `deviceId: ""`, timeout 35 s.
4. Receipt `cmdError: 10`: show "Press OK on the G1".
5. `success`: send `BT:Pair:Result {"result":"success"}` with envelope `deviceId` set, timeout 10 s.
6. `success`: store identity and peripheral id, go live. `cmdError: 11`: "Declined, timed out, or
   the probe is not in the dock". Nothing is stored on failure.

Pairing makes the phone the G1's owner and kicks out the official app or the Python client. Say so
on the pair screen.

### Live data [HW]

`WT10:status:report` arrives every 2 s unasked. Keep only the latest report in state. Mark the
screen stale after 6 s without one. A docked probe has only `probeColor`, `cookingState`,
`cookingMode`, `setParams`; render it as "Docked, charging".

## Screens

**PairScreen**: the steps above, one status line, one button.

**LiveScreen**: base battery and connection state in a header. One card per probe:

- core temperature, large (`curTemperature`)
- ambient (`curAmbientTemperature`), target (`setParams[0].setTemperature`)
- the five `areaTemperature` zones as a small bar, tip first
- cooking state, mode, elapsed `curCookSec` as `h:mm:ss`, probe battery
- button: "Start cook" when docked or idle, "Change target" while cooking

**CookModal**: Manual / Smart toggle, target temperature stepper in the display unit, Start.

- Start: `WT10:cooking:action`, `cookingAction: 1`, new `cookUuid`, `startClient: "android"`,
  `cookingData: {"dataType": "manual", "dataId": "", "dataName": "Manual cook" | "Smart cook",
  "dataImgUrl": ""}`.
- Change target: same action with the **running** `cookUuid` and its `startClient`;
  `cookingData: null` when `startClient` is `device`.
- Confirm by watching the next status report, not only the receipt.
- Target range: 30 to 100 °C (86 to 212 °F) until the official app's limits are read from the APK.
  This is an assumption.

**SettingsModal**: volume (`high` / `medium` / `quiet` / `mute`) via `WT10:setting:modify`
[HW]; °C / °F (local only); "Forget this G1" (deletes stored identity; does not unbind the device).

## Units

All temperatures on the wire are integer tenths of a degree Fahrenheit, regardless of the unit the
trust message or the G1's screen uses [HW]. Convert only at the UI edge:
`c = (t / 10 - 32) * 5 / 9`, and `t = Math.round((c * 9 / 5 + 32) * 10)` when sending.

## Errors

Map receipts to plain messages: `cmdError 11` refused / not owner, `4` "not valid in this cook
state", timeout "No reply from the G1". Drop frames that fail CRC or JSON parse, log the error
with the frame length, and keep the session alive. Never show raw JSON to the user; keep a
debug log screen behind a long press on the header for hardware testing.

## Verification

- **Protocol unit tests (vitest)**: fixtures produced by `g1.py` (`pack` output, a fragmented
  >255-byte payload, a captured status report frame). Assert TS `unpack` matches, TS `pack`
  round-trips through Python `unpack`, CRC check value `0x31C3`, and fragment boundaries. These
  catch byte-level regressions that a hardware run cannot localise.
- **Hardware acceptance (manual, real G1, Android 12+ phone)**, recorded as a checklist in the PR:
  1. Fresh install, deny then grant permissions: the app recovers without restart.
  2. Pair with probe docked; press OK; app goes live within 5 s.
  3. Kill the app, reopen: live without touching the G1.
  4. Undock probe, start Manual 60 °C: the G1 screen shows 60 °C, the card shows cooking.
  5. Change target to 65 °C: same cook, timer keeps counting.
  6. Set volume to mute: receipt success, the G1 is silent.
  7. Walk out of range and back: reconnects without user action.
- No emulator E2E for BLE: the Android emulator has no Bluetooth. UI-only Maestro flows are a
  later option if the screens grow.

## Build order

1. Verify raw-block zstd on hardware with `g1.py` (above). About 15 minutes.
2. `src/protocol` + vitest fixtures. About 2 hours.
3. Add BLE deps and plugin config, `G1Session`, a debug screen that pairs and prints reports.
   First hardware milestone. About half a day, mostly MTU and permission edge cases.
4. `useG1` state machine, LiveScreen. About half a day.
5. CookModal and SettingsModal, then the hardware acceptance checklist. About half a day.

3. Target temperature limits in the official app.
